Enrichment Data & Flow — for the Stockfolio Client

This is the field-by-field reference for everything stockfolio-insights produces and how it gets from a raw API call into the payload the Stockfolio frontend renders. It complements CLAUDE.md (which covers why decisions were made); this doc covers what fields exist and what they mean.

Not investment advice. momentum is sentiment velocity, not a price signal. Every derived label (typology tags, insider signal, squeeze risk) ships next to its raw inputs so the UI can show why, never just a verdict.

1. High-level flow

                         ┌─────────────────────────────────────────────┐
                         │              MongoDB Atlas (shared)          │
                         │        stockfolio-insights DB, collections   │
                         └─────────────────────────────────────────────┘
                                   ▲              ▲              ▲
        WORKERS (write-only)      │              │              │        API (read-only)
   ─────────────────────────      │              │              │      ──────────────────
   worker:ingest   */20min ───────┘              │              │      GET /insights/*
     Finnhub + Yahoo news → LLM tag → aggregate   │              │      GET /events/*
                                                   │              │      GET /typology/*
   worker:calendar daily ────────────────────────┘              │      GET /quotes/*
     earnings, filings, ownership, analyst,                     │      GET /enrich/:ticker
     short interest, macro, prices, typology                    │        (composed, cached)
                                                                  │
   worker:quotes    */5min ───────────────────────────────────────┘
     Yahoo v8 chart quotes + daily Finnhub profile

All three workers start from the same dynamic watchlist (getActiveTickers() — src/services/watchlist.js): portfolio tier (synced from Stockfolio positions) > manual (env-pinned) > watchlist tier (synced from Stockfolio watchlists) > discovery (news-mentioned ≥5×/7d, 30-day decay, cap 150 tickers total for API budget).

The Stockfolio backend reads this service's data two ways:

  1. GET /enrich/:ticker over HTTP — the composed Position-page payload (see §4).
  2. Direct MongoDB read of individual collections via mongoose.connection.useDb() on the same Atlas cluster — no dependency on this service's API process being up. See Portfolio/server/services/stockfolioInsightsService.js.

4. GET /enrich/:ticker — the composed Position-page payload

Single call, 5-minute in-memory TTL cache (x-cache: hit|miss response header). Every field degrades to null/[]/false if the underlying data isn't available yet — the client should never assume a field is present and should render around gaps rather than erroring.

{
  "ticker": "AAPL",
  "generatedAt": "2026-07-21T12:00:00.000Z",
  "summary": { ... },        // §4.1 — precomputed badge/chip numbers
  "typology": { ... },       // §4.2 — archetype tags
  "priceSeries": [ ... ],    // §4.3 — 30d OHLCV+volume for a sparkline/chart
  "surpriseHistory": [ ... ],// §4.4 — up to 8 past earnings beats/misses
  "analystTrends": [ ... ],  // §4.5 — last 3 months of rec counts
  "shortInterest": { ... },  // §4.6 — latest FINRA snapshot
  "sentimentSeries": [ ... ],// §4.7 — 14d sentiment/article-count series
  "headlines": [ ... ],      // §4.8 — 5 latest tagged articles (7d window)
  "nextEvent": { ... },      // §4.9 — next upcoming CorporateEvent
  "recentEvents": [ ... ],   // §4.9 — last 3 past CorporateEvents
  "ownership": { ... }       // §4.10 — latest OwnershipSnapshot
}

4.2 typology

Subset of TickerTypology: tags[], primaryIndustry, marketCapClass, style, volatilityClass. Full dimension definitions in §7.

4.3 priceSeries

Last 30 PriceStat days, ascending by date: { date, close, volume, volumeRatio }.

4.4 surpriseHistory

Up to 8 most recent reported-earnings CorporateEvent docs (type earnings, has epsActual): { date, period, epsActual, epsEstimate, surprisePct }.

4.5 analystTrends

Last 3 AnalystTrend docs, newest first: { period, strongBuy, buy, hold, sell, strongSell }. The signal is the month-over-month change, not the absolute counts — that's what summary.analystDelta gives you pre-computed.

4.6 shortInterest

Latest ShortInterest doc in full: { settlementDate, shortInterest, avgDailyVolume, daysToCover, changePct, source }.

4.7 sentimentSeries

Last 14 TickerInsight days, ascending: { date, sentiment, articles }. Feeds a sparkline.

4.8 headlines

Up to 5 most recent analyzed articles mentioning this ticker, within the last 7 days: { headline, url, publishedAt, sentiment, themes, llmSummary }.

4.9 nextEvent / recentEvents

Full CorporateEvent docs — see §7 field table. nextEvent is the single soonest future event; recentEvents is up to 3 most recent past events.

4.10 ownership

Full latest OwnershipSnapshot doc — see §7. topHolders is currently always empty (13F institutional data deliberately deferred — schema is ready, not populated; see CLAUDE.md).

6. GET /quotes and GET /quotes/:ticker — live-ish price data

Separate from /enrich — quotes refresh on their own 5-minute cycle and are the only "live" numbers in this service. /enrich's summary.lastChangePct is the prior daily close, not the live quote — for a live price/change badge, the client must call /quotes.

  • GET /quotes?tickers=AAPL,MSFT,PLTR — batch, up to 100 tickers (Watchlist grid)
  • GET /quotes/:ticker — single (Position page live price)

Response shape (shape() in src/routes/quotes.js):

FieldNotes
price, change, changePct, previousClose, dayHigh, dayLow, volumeFast fields, refreshed every ~5 min from Yahoo v8 chart
marketStatePRE | REGULAR | POST | CLOSED
name, exchange, currency, fiftyTwoWeekHigh/Low, marketCap, peRatio, eps, dividendYield, beta, logoSlow fields, refreshed daily from Finnhub profile
ageSecondsSeconds since quoteUpdatedAt
staletrue if ageSeconds > 600 (configurable via QUOTE_STALE_SECONDS) or quote never fetched

Client fallback contract: the UI reads /quotes as primary source. It should call Yahoo directly only for tickers returned in the batch response's missing[] array, or any row with stale: true. Fetching a missing/unknown ticker auto-subscribes it (WatchedTicker tier discovery) so the next 5-min poll cycle picks it up going forward — the gap self-heals, it doesn't need to be re-fetched from Yahoo forever.

How insiderNet3m is actually computed (§4.10 / §7 OwnershipSnapshot)

Endpoint: Finnhub free tier, GET /stock/insider-transactions?symbol=X&from=<90d ago> (refreshOwnership() in src/services/ownership.js), called once per active ticker, once a day, from worker:calendar.

  1. Finnhub returns every insider Form-4-derived transaction (officers, directors, 10%+ holders) reported in the trailing 90 days for that ticker.
  2. We sum each transaction's change field (positive = shares acquired, negative = shares disposed) across the whole batch → insiderNet3m. Transaction count is stored separately as insiderTxCount3m.
  3. Both are upserted into OwnershipSnapshot keyed on (ticker, asOf: today at UTC midnight) — so it's a daily snapshot, not a running total; each day's document re-derives the sum from the last 90 days as of that day.
  4. computeTypology() (src/services/typology.js) reads the latest snapshot and buckets it into insiderSignal: buying (net > 0), selling (net < 0), neutral (net = 0), unknown (no snapshot yet). buying also adds the insider-buying chip tag.

Nothing here requires an LLM or judgement call — it's a direct sum of Finnhub's reported transactions. If FINNHUB_API_KEY is unset or the call errors, the ticker's insider fields stay unknown/null rather than retrying — same degrade-gracefully pattern as everything else in this service. There is currently no institutional (13F) counterpart — see §8.

How tickers get connected on the /typology/map — no graph, a shared label

GET /typology/map?group=primaryIndustry (or style/marketCapClass/volatilityClass, src/routes/typology.js) is not a correlation, co-occurrence, or similarity graph. It's a $group aggregation over TickerTypology.primaryIndustry — tickers only end up in the same bucket because they were independently assigned the same industry string. The pipeline behind that string:

  1. Per-article LLM tagging (worker:ingest, analyzePendingArticles() in src/services/analyzer.js): every news article is sent to gpt-4o-mini in batches of 20. The prompt asks the model to read the headline/summary and return, per article, which tickers it's about and a lowercase industries[] guess from a suggested (not enforced) list — semiconductors, banking, energy, defense, healthcare, real-estate, software, retail, automotive, telecom, other. Stored on the Article doc.
  2. Per-ticker rollup (worker:calendar, computeTypology() in src/services/typology.js): for a given ticker, aggregate the last 7 days of its analyzed articles, $unwind their industries[], count frequency, take the top 5. The single most frequent becomes primaryIndustry; all 5 are kept as industries[].
  3. The map groups on that field. Two tickers appear "connected" on the map purely because the LLM tagged their respective recent news with the same industry word — there's no pairwise comparison between tickers, no embedding distance, no shared-ownership or sector-classification-provider data involved.

Practical implications for the client:

  • The grouping can be noisy/inconsistent — the LLM isn't given a fixed enum, so near-synonyms (e.g. "software" vs "tech") could theoretically split a bucket. Worth normalizing server-side if this becomes visible in the UI.
  • A ticker with no news in the last 7 days has primaryIndustry: undefined → falls into the unknown bucket ($ifNull in the aggregation), not omitted from the map.
  • Switching group= to style/marketCapClass/volatilityClass uses deterministic numeric thresholds instead (see dimension table above) — those groupings are stable/reproducible, unlike primaryIndustry which can drift day to day as news volume and LLM tagging shift.

8. Gaps the client should design around today

These are known, not bugs to chase — see CLAUDE.md "Known gaps" for full detail:

  1. ownership.topHolders is always [] — 13F institutional data deliberately deferred. Render insider-only ownership info; don't build UI expecting institutional breakdowns yet.
  2. priceSeries/volumeRatio/unusualVolume are currently empty/false for all tickers — Stooq is blocking requests (since 2026-07-19). Don't treat an empty price chart as "no volume anomaly," treat it as "data temporarily unavailable."
  3. No TASE (.TA) events/filings — EDGAR and Stooq both skip non-US tickers gracefully (null fields, no crash). A Maya-sourced CorporateEvent/Article path is planned but not built.
  4. Every summary.* field can independently be null — badges should render conditionally per-field, not gate the whole card on one field being present.
